Engineering walkthrough

How the BC Assessment service works

A file-by-file, function-by-function tour of a FastAPI property-lookup service — and of the four defects that once made it hang and lie. Every design choice here exists to answer one of those defects, so the code and the incident are told together.

The service answers a single question: given a formatted address, what does BC Assessment say this property is worth? It checks a SQLite cache; on a miss it drives a real Chromium browser through bcassessment.ca with Playwright, parses the result with BeautifulSoup, and caches it. That is the easy version. The hard version — the reason this codebase exists — is making it do that reliably, for hours, under concurrent load, without silently returning the wrong property.

FastAPI + async Playwright / Chromium BeautifulSoup + lxml SQLite (WAL) Telegram alerts

Orientation

The request pipeline

One call to GET /address travels through eight stages across several modules. The ordering is not incidental — two of these stages sit in a specific place precisely because a naive ordering caused the original hang. This is a genuine sequence, so it is worth walking in order.

Validate & normalize — lookup_by_address()

Trim the address; reject empty input early. Normalize to upper-case, single-spaced text so "7009 tisdall st" and "7009 TISDALL ST" share one cache key.

Positive cache — cache_get()

A hit on a valid, unexpired row returns immediately. No browser, no network, no rate-limit cost. This is the whole point of the cache.

Negative cache — get_negative_cache()

If this exact address was recently confirmed not found, return that without re-scraping. Unknown addresses otherwise burn the rate-limit budget on every request.

Rate limit — bc_rate_limiter.acquire(max_wait=…)

Wait for the minimum spacing and window/hourly caps before taking the scrape slot (acquiring it inside the lock was the hang), and only while the projected wait stays under SCRAPE_MAX_PROJECTED_WAIT_SECONDS. Beyond that the caller gets busy with a Retry-After header instead of hanging.

Queue guard + priority scrape slot + total timeout — _run_scrape()

Shed load past a queue depth (busy), then serialize scrapes through a single-slot ScrapeGate, where a waiting live request always goes before batch work, under a hard per-lookup ceiling so one stuck scrape can never wedge the service.

Fresh context → scrape steps — lookup_context() + scrape_address()

A brand-new browser context and page per lookup. Load home, type the address, wait for autocomplete, open the property, confirm it rendered, extract HTML.

Classify — FailureType

Every outcome is either a success or a typed failure: not_found, blocked, timeout, parse_empty, error, or busy.

Record & alert — _record_outcome()

Valid results go to the cache; failures go to a retry queue with reason/step/URL/snapshot; blocks fire a de-duplicated Telegram alert; recovery sends one all-clear.

Orientation

The root cause of the outage

Before the code makes sense, the incident it answers must be clear. The old service worked after a restart and rotted within hours, so a systemd timer restarted it every two hours. A restart only clears two things — process memory and the cookie jar — which is exactly what tells you where the bug lived. Four defects compounded:

Defect 1 — the scraper never returned to a clean page

A guard checked if page.locator("#rsbSearch").count() > 0: return to decide "already home." But BC's result pages carry that same search box in their header, so after the first lookup the guard short-circuited forever and every later search ran on the previous property's page.

Defect 2 — that produced silently wrong data, not just hangs

Readiness was a text regex: /Total value \$[\d,]+/. Because of Defect 1 the DOM still showed the previous property's total value, so the wait returned immediately from stale markup, and the old numbers were cached under the new address. This is data corruption — plausible but wrong values.

Defect 3 — the browser and context were never recycled

The error path closed the page, but the context and browser lived for the whole process. Cookies, storage and Chromium memory accumulated until BC's bot mitigation served a challenge — after which every lookup timed out and every answer became "Property not found," permanently, until the next restart.

Defect 4 — the actual hang: rate-limit sleeps held the scrape lock

The scrape acquired _scrape_lock, then called bc_rate_limiter.acquire() inside it. At the hourly cap, one request slept up to an hour while holding the semaphore, freezing every queued request behind it.

And why every failure looked identical

A blanket except Exception: return None collapsed timeouts, challenge pages, network errors and genuinely unknown addresses into one None, which the API reported as "Property not found." Nobody could tell a blocked scraper from a nonexistent address. The redesign's spine — the FailureType enum — exists to end exactly that.

Contract app/schemas.py

The data vocabulary of the whole service: the failure taxonomy, the result of one lookup attempt, and the exact JSON shapes the API returns. It is loaded first here because every other module speaks in these types.

class FailureType(str, Enum)

Six named reasons a lookup produced no usable result. Subclassing str means the value serializes straight into JSON as "not_found", "blocked", etc.

class FailureType(str, Enum):
    NOT_FOUND   = "not_found"    # autocomplete returned no real suggestion
    BLOCKED     = "blocked"      # challenge / 403 / 429 / redirected off-site
    TIMEOUT     = "timeout"      # a step exceeded its budget
    PARSE_EMPTY = "parse_empty"  # page loaded but carried no total_value
    ERROR       = "error"        # anything else
    BUSY        = "busy"         # too many queued; caller should retry

Why it exists

This enum is the direct answer to "every failure looked identical." A blocked scraper and a fake address are now different values with different handling, different API messages, and different alerting.

FailureType.is_scraper_fault -> bool

A single predicate that encodes the most important distinction in the system: is this failure ours (or BC's), or is it the caller's address simply not existing?

@property
def is_scraper_fault(self) -> bool:
    return self is not FailureType.NOT_FOUND
Invariant

Only NOT_FOUND is "not our fault." Health scoring, browser recycling and negative caching all branch on this one line — a run of unknown addresses must never be mistaken for a sick scraper.

@dataclass LookupOutcome

The value every lookup path returns. It carries not just success/failure but enough forensic context to alert and retry: the reason, the page URL, the named step that broke, whether the browser was restarted, and any saved HTML snapshot.

@dataclass
class LookupOutcome:
    result: Optional[AssessmentResult] = None
    failure: Optional[FailureType] = None
    reason: Optional[str] = None
    url: Optional[str] = None
    step: Optional[str] = None
    restarted: bool = False
    snapshot_path: Optional[str] = None

    @property
    def ok(self) -> bool:
        return self.result is not None and self.failure is None

Why the two factory methods

LookupOutcome.success(result) and LookupOutcome.failed(type, reason, …) keep construction uniform and impossible to get half-right — you cannot accidentally build an "outcome" that is both a success and a failure. ok is the one place that definition lives.

AssessmentResult · AssessmentData · SuccessResponse · ErrorResponse

Pydantic models that pin the response bytes. The success envelope — {"status":"success","data":{"result":{…},"status":200}} — is a contract with the consuming BlueNest client and must not drift.

class ErrorResponse(BaseModel):
    status: str = "error"
    message: str = ""
    # Additive: lets callers tell "no such property" from "scraper blocked".
    # Clients reading only status/message are unaffected.
    error_type: Optional[str] = None
Invariant

Success, and the exact string "Property not found", stay byte-for-byte identical to the old service. error_type is purely additive — new information that never breaks an existing reader.

Contract app/config.py

A single settings object built from .env at import time. Every tunable — timeouts, rate limits, browser recycling thresholds, Telegram credentials — lives here so behaviour is configured, not hard-coded.

class Settings(BaseSettings) · settings = Settings()

Pydantic-settings reads each field from the environment / .env, with typed defaults. The module exposes one shared settings singleton.

scrape_cache_ttl_seconds: int = 0        # 0 = never expire (BC updates ~yearly)
scrape_total_timeout_ms: int = 60_000    # hard ceiling on one whole lookup
browser_max_lookups: int = 200           # recycle Chromium after N lookups
telegram_bot_token: str = ""            # set in .env ONLY; never commit a token

    model_config = SettingsConfigDict(env_file=".env", extra="ignore")

Why a singleton read at call time

Modules read settings.field when they need it rather than capturing the value at import. That is what lets a test do monkeypatch.setattr(settings, "field", value) and have the live code pick it up — no dependency-injection plumbing required.

The fix — security

The Telegram token used to be a hard-coded default in this file. It is now an empty string; credentials come from .env only (which is gitignored), and a regression test asserts the defaults ship with no secret.

Settings.get_telegram_chat_ids() -> list[int]

Parses the comma-separated TELEGRAM_CHAT_IDS string into integers, skipping anything malformed instead of raising.

for part in self.telegram_chat_ids.split(","):
    try:
        ids.append(int(part.strip()))
    except ValueError:
        # A malformed chat id must not take the whole service
        # down at import time. Skip it and carry on.
        continue

Problem it solves

Config is parsed once at process start. A single typo in an ops-managed .env should degrade alerting for one recipient, never prevent the service from booting.

API app/main.py

The FastAPI surface: five routes plus a lifespan that owns startup and shutdown. The route handlers stay thin — they translate between HTTP and the lookup engine and nothing more.

@asynccontextmanager async def lifespan(app)

Runs once at boot and once at shutdown. On boot it creates the DB schema and warms the browser so the first request is not slowed by a cold Chromium launch; on shutdown it tears the browser down, flushes any in-flight alerts, and closes the SQLite connection cleanly.

async def lifespan(_app):
    init_db()
    await warmup_browser()
    try:
        yield
    finally:
        await shutdown_browser()
        await flush_pending()      # let queued Telegram alerts finish
        close_connection()

Why lifespan and not on_event

A context manager guarantees the finally block runs on every shutdown path, so the browser process and DB handle are never leaked between restarts.

@app.get("/address") async def get_address(address)

The only route the consumer cares about. It trims input, rejects empty strings with a clear error, delegates the real work to lookup_by_address, and maps the typed outcome onto the response contract.

outcome = await lookup_by_address(address)

if outcome.ok and outcome.result is not None:
    return SuccessResponse(data=AssessmentData(result=outcome.result, status=200))

failure = outcome.failure or FailureType.ERROR
return ErrorResponse(
    status="error",
    message=_FAILURE_MESSAGES.get(failure, "Lookup failed"),
    error_type=failure.value,          # the additive field
)

The mapping that preserves the contract

_FAILURE_MESSAGES maps NOT_FOUND → "Property not found" (unchanged) while blocked/timeout/busy get their own human messages. Old clients read the same status/message; new clients can additionally branch on error_type.

@app.get("/health") async def health()

Reports real scraper health, not mere process liveness — and returns HTTP 503 when the browser has failed repeatedly.

if not browser_manager.is_healthy:
    return JSONResponse(status_code=503, content=body)
return body   # includes provider, cache size, unresolved failures, browser stats
The fix — observability

The old service answered "200 OK" while its browser was wedged. Now a monitor, or systemd, can see a dead scraper behind a running process. This is what lets you retire the blind 2-hour restart.

/stats · /failures · POST /failures/retry

The operations surface. /stats returns counters plus unresolved-failure counts and cache size; /failures lets you inspect the retry queue (with ?due_only / ?include_resolved); POST /failures/retry re-attempts failures whose backoff has elapsed.

@app.post("/failures/retry")
async def retry_failures(limit: int = Query(10, ge=1, le=100)):
    return await retry_failed_lookups(limit=limit)

Why these exist

They turn "the scraper is failing" from an opaque log grep into an inspectable, actionable queue — directly serving the PRD's requirement that failed addresses be stored for retry and later investigation.

Engine app/services/lookup.py

The orchestrator — the heart of the redesign. It sequences cache → negative cache → rate limit → single-flight scrape → classify → record, and it is where Defect 4 (the hang) is structurally fixed by ordering.

_normalize_address(address) -> str

Collapses whitespace and upper-cases, so every spelling of the same address maps to one cache key.

return re.sub(r"\s+", " ", address.strip().upper())

Why it matters

The cache and the negative cache are only useful if "7009 Tisdall St" and "7009 TISDALL ST" collide on purpose. Normalization is what makes a "repeated address" actually hit.

_mock_lookup(address) -> LookupOutcome

The provider used when LOOKUP_PROVIDER=mock. It runs the entire request path with no browser and no network, deriving deterministic figures from a hash of the address.

digest = int(hashlib.sha1(upper.encode()).hexdigest()[:6], 16)
return LookupOutcome.success(AssessmentResult(
    total_value=f"${500_000 + digest % 1_500_000:,}", ...))

Two jobs

First, tests and local dev exercise the full API without Playwright. Second, because each address yields distinct figures, the load harness can assert that two different addresses never return the same total_value — the regression test for Defect 2. Magic tokens (NOWHERE, BLOCKED) drive the failure branches.

async def _run_scrape(address) -> LookupOutcome

The concurrency-critical core. It applies a queue-depth guard, registers live demand so batch work yields, acquires the rate limiter before the slot with a bounded wait, then runs one scrape at a time under a hard total timeout. _run_scrape(address, batch=True) is the batch worker's path: it never sheds load and sleeps only outside the slot.

async with _queue_lock:
    if max_depth > 0 and _queue_depth >= max_depth:
        return LookupOutcome.failed(FailureType.BUSY, ...)   # shed load fast
    _queue_depth += 1

async with _scrape_gate.live_demand():             # batch yields slot + tokens to us
    # Outside the scrape slot on purpose — this is the Defect 4 fix.
    wait = await bc_rate_limiter.acquire(max_wait=settings.scrape_max_projected_wait_seconds)
    if wait is not None:
        return _busy(..., wait)                     # busy + Retry-After, never an hour-long hang
    async with _scrape_gate.slot():                 # single-flight, live before batch
        return await _scrape_with_ceiling(address)

# _scrape_with_ceiling:
    try:
        return await asyncio.wait_for(
            _scrape_once(address),
            timeout=settings.scrape_total_timeout_ms / 1000)   # hard ceiling
    except asyncio.TimeoutError:
        browser_manager.request_restart("lookup exceeded total timeout")
        return LookupOutcome.failed(FailureType.TIMEOUT, ..., step="total_timeout")
The fix — Defect 4 (the hang)

Rate limiting now happens before _scrape_lock, so a request sleeping at the hourly cap no longer holds the semaphore that every other request needs. Two more guards back it up: the queue-depth check returns a fast busy instead of letting callers pile up unboundedly, and asyncio.wait_for caps any single scrape — on breach it flags the browser for relaunch, because a lookup that blew its whole budget means Chromium is in a bad state.

The edge that used to remain — now closed

The first fix left a capped-out hourly wait unbounded: waiters serialized on the limiter's own lock, outside the total timeout, so a request could block for up to an hour. The limiter now reports projected_wait() without sleeping and never holds a lock while waiting, and /address answers busy with Retry-After within about a second once the projected wait exceeds the threshold. The busy body and its HTTP 200 status are unchanged; the header is additive.

async def lookup_by_address(address) -> LookupOutcome

The public entry point that stitches the pipeline together in exactly the order shown at the top of this page.

# 1. Positive cache
cached = await asyncio.to_thread(cache_get, normalized)
if cached is not None and is_valid_assessment(cached):
    await record_cache_hit(address);  return LookupOutcome.success(cached)

# 2. Negative cache — a recent, genuine "not found"
negative = await asyncio.to_thread(failures.get_negative_cache, normalized)
if negative is not None:
    await record_cache_hit(address);  return LookupOutcome.failed(FailureType.NOT_FOUND, negative)

# 3. Scrape (mock or live)
await record_bc_scrape(address)
outcome = _mock_lookup(address) if mock else await _run_scrape(address)
await _record_outcome(address, normalized, outcome)

Why the blocking DB calls go through asyncio.to_thread

SQLite calls are synchronous. Wrapping them in to_thread keeps them off the event loop so a disk hiccup can't stall unrelated async requests. Note the scrape counter increments before dispatch, so it reflects exactly the traffic the cache is meant to eliminate.

async def _record_outcome(address, normalized, outcome)

The single place results are persisted and alerted. Success and each failure class are handled distinctly.

if outcome.ok and outcome.result is not None:
    browser_manager.record_success()
    await asyncio.to_thread(cache_set, normalized, outcome.result)
    await asyncio.to_thread(failures.mark_resolved, normalized)  # clear old failure
    await notify_recovered(address);  return

if failure is FailureType.BUSY:
    return   # load-shed, not a scraper fault — do not queue for retry

browser_manager.record_failure(failure)
await asyncio.to_thread(failures.record_failure, address, normalized, failure, ...)
Invariant

Only valid results reach cache_set; every failure goes to the failed_lookups queue instead. BUSY is deliberately not queued — it says nothing about browser health, only that the service was momentarily overloaded.

warmup_browser() · shutdown_browser() · retry_failed_lookups(limit)

Lifecycle and maintenance helpers. Warmup pre-launches Chromium at boot (skipped in mock mode); shutdown tears it down; retry walks due failures and re-runs them through the normal path — skipping not_found, which is answered from the negative cache and needs no browser.

for row in due:
    if row["failure_type"] == FailureType.NOT_FOUND.value:
        continue                      # negative cache already covers these
    outcome = await lookup_by_address(row["address"])
    if outcome.ok: recovered += 1
Engine app/services/browser.py

The Playwright lifecycle manager: one long-lived browser process, but a brand-new context and page for every single lookup. This file is where Defects 1, 2 and 3 are removed at the root rather than patched.

async def _route_handler(route)

A request interceptor installed on every context. It aborts images, media and fonts, and known trackers (analytics, tag managers, Facebook, Hotjar…), letting everything else through.

if request.resource_type in _BLOCKED_RESOURCE_TYPES:   # image / media / font
    await route.abort();  return
if _BLOCKED_URL_RE.search(request.url):                  # trackers
    await route.abort();  return
await route.continue_()

Why block resources

The scraper needs the page's text, not its pictures. Dropping heavy and irrelevant requests speeds every lookup and shrinks Chromium's memory footprint — a performance win that costs nothing in correctness. The whole handler is wrapped so a route failing mid-teardown can never surface as a lookup error.

@dataclass BrowserHealth

The mutable health record behind /health: consecutive failures, lookups since launch, totals, timestamps, last failure type, and restart count. as_dict() renders it for the health endpoint.

consecutive_failures: int = 0
lookups_since_browser_launch: int = 0
last_failure_type: Optional[str] = None
restarts: int = 0

Purpose

These counters are the evidence base for two automatic decisions: when to recycle the browser, and when to declare the service unhealthy.

record_success() · record_failure(failure)

Update the health record after each lookup. Success resets the consecutive-failure streak; failure advances it — but with a crucial exception.

def record_failure(self, failure):
    self._health.total_lookups += 1
    self._health.lookups_since_browser_launch += 1
    # A genuine NOT_FOUND means the address doesn't exist, not that
    # the scraper is sick. Don't let it drive /health to 503.
    if not failure.is_scraper_fault:
        return
    self._health.consecutive_failures += 1
    if self._health.consecutive_failures >= settings.browser_restart_after_failures:
        self.request_restart(f"{...} consecutive failures")
Invariant

A run of unknown addresses is normal traffic. If not_found counted toward "unhealthy," ordinary lookups would push /health to 503, a monitor would restart the service, and the restart loop this work removed would quietly return. The is_scraper_fault guard is what prevents that.

_needs_restart() -> (bool, reason) · ensure_browser() -> bool

ensure_browser lazily launches Chromium, and relaunches it whenever _needs_restart says so: no browser, a disconnected browser, a pending restart request, or the per-browser lookup budget reached.

def _needs_restart(self):
    if self._browser is None:                 return True, "no browser"
    if not self._browser.is_connected():      return True, "browser disconnected"
    if self._restart_pending:                 return True, self._restart_reason
    if lookups_since_launch >= max_lookups:   return True, "reached N lookups"
    return False, ""
The fix — Defect 3

The browser is now recycled: after BROWSER_MAX_LOOKUPS, after too many consecutive failures, or on disconnect. Recycling drops the accumulated cookies and Chromium memory that used to build up until BC served a challenge page. An asyncio.Lock around launch means concurrent callers can't spawn two browsers.

@asynccontextmanager async def lookup_context() -> (Page, restarted)

The single sanctioned way to obtain a page. It creates a fresh context, installs the route filter, yields a clean page, and always closes the context in finally.

context = await browser.new_context(user_agent=USER_AGENT,
                                     viewport={...}, locale="en-CA")
await context.route("**/*", _route_handler)
page = await context.new_page()
try:
    yield page, restarted
finally:
    await context.close()      # no DOM or cookie state survives to the next lookup
The fix — Defects 1 & 2

A fresh context per lookup makes stale markup impossible, not merely unlikely. There is no previous property's page to short-circuit on, and no previous "Total value" left in the DOM for the readiness check to match. The two data-corruption defects are removed structurally: the state that carried the bug no longer exists between lookups. The browser process is reused (cheap); only the ~200–400 ms context is rebuilt (correct).

Engine app/services/scraper.py

The named scraping steps, block detection, and HTML parsing. Every step is labeled so a failure reports where it broke, and every exit is a classified FailureType — never a bare None.

parse_html(html) · _find_value_after_label() · _find_total_value()

Turn the property page into an AssessmentResult. _find_total_value regex-scans the whole page text for "Total value $…"; _find_value_after_label locates a label node and reads the sibling/row value beside it, which survives BC's inconsistent markup better than fixed CSS paths.

try:
    soup = BeautifulSoup(html, "lxml")        # fast, forgiving on malformed markup
except Exception:
    soup = BeautifulSoup(html, "html.parser")  # stdlib fallback

Why label-relative parsing

BC Assessment's layout is not stable, so "find the text next to the word Bedrooms" is more robust than a brittle selector chain. lxml is preferred for speed and tolerance, with the stdlib parser as a safety net.

detect_block(html, url, status) -> Optional[str]

The block detector, run at multiple points in the scrape. It layers three cheap checks and returns a human-readable reason string (or None).

if status is not None and status >= 400:
    return f"HTTP {status} from BC Assessment"          # 403 / 429 / 5xx
if url and "bcassessment.ca" not in url:
    return f"redirected off-site to {url}"            # WAF bounce
for marker in _BLOCK_MARKERS:                         # "captcha", "unusual traffic"…
    if marker in lowered:
        return f"block marker: {marker!r}"
The fix — separating "blocked" from everything else

Checking HTTP status, off-site redirects and content markers before falling back to a timeout classification is what lets the service say "we are being blocked" instead of misreporting a challenge page as "Property not found." It runs on the home page, on a missing search box, on a stalled result, and on the final HTML.

save_snapshot(address, html) · _prune_snapshots(root)

When a page looks blocked or unexpected, its HTML is written to data/snapshots/ with a timestamped, hashed filename; old snapshots beyond SNAPSHOT_KEEP are pruned.

path = root / f"{stamp}_{digest}.html"
path.write_text(html, encoding="utf-8", errors="replace")
_prune_snapshots(root)   # keep only the newest SNAPSHOT_KEEP files

Purpose

A block can't always be reproduced on demand, so the evidence is captured the moment it happens. The snapshot path travels on the LookupOutcome into both the retry queue and the Telegram alert.

async def scrape_address(page, address, *, restarted)

The lookup itself, as five named steps on a guaranteed-clean page. Each step sets a step label, and any failure returns a classified outcome carrying that label.

step = "goto_home"        # 1. load home; detect_block on the response
step = "await_search_box"  #    wait for #rsbSearch (block vs timeout on miss)
step = "fill_search"      # 2. click + fill the address (fill, as BC's autocomplete needs)
step = "await_autocomplete"# 3. wait for suggestions; else _classify_missing_autocomplete
step = "click_suggestion" # 4. open the first real suggestion
step = "await_result_nav" #    wait for URL change AND the readiness predicate
step = "extract_html"     # 5. re-check block, then parse
step = "parse"            #    PARSE_EMPTY if no total_value survived

Why every step is named

"It failed" is not actionable; "it failed at await_autocomplete on this URL for this address" is. The label flows into logs, the retry queue and alerts, so a bad lookup can be traced without reproducing it. A trailing try/except converts any Playwright timeout into TIMEOUT and anything else into ERROR, both tagged with the step that was live.

Invariant

Because lookup_context() hands over a fresh page, the readiness check /Total value \$[\d,]+/ is trustworthy again — there is no prior property's value in the DOM to satisfy it early. The same regex that was dangerous in the old code is safe here purely because the state it reads is clean.

async def _classify_missing_autocomplete(page, address, *, step, restarted)

The judgement call the old code could not make: when no suggestion appears, is the address unknown, or is the scraper in trouble?

reason = detect_block(html, url, None)
if reason:
    return LookupOutcome.failed(FailureType.BLOCKED, reason, ...)

search_alive = await page.locator(SEARCH_SELECTOR).count() > 0
typed        = await page.locator(SEARCH_SELECTOR).first.input_value(...)

if search_alive and typed.strip():
    # Page healthy, our text still in the box, no block → genuinely unknown
    return LookupOutcome.failed(FailureType.NOT_FOUND, "no suggestion for this address", ...)

return LookupOutcome.failed(FailureType.TIMEOUT, "autocomplete never appeared…", ...)
The fix — not_found vs timeout vs blocked

This is the exact ambiguity that turned every failure into "Property not found." The heuristic checks block markers first, then whether the page is otherwise healthy (search box present, our text still in it). Only a healthy page with no suggestion is a true NOT_FOUND; anything else is a scraper fault that must be retried, not cached.

Engine app/services/rate_limit.py

Composable limiters that together keep the service a polite guest on bcassessment.ca: a minimum spacing between requests, a short-window cap, an hourly cap, and a batch-only share of that hourly cap. Each can say how long the next call would wait without sleeping. Cache hits are never rate-limited — only real BC visits.

class BCRateLimiter — sliding-window cap

Allows at most max_calls BC operations per window_seconds, using a deque of timestamps. projected_wait() reports how long until the oldest timestamp ages out; record() takes a slot. Asking never consumes anything.

def projected_wait(self, now):
    self._prune(now)                          # drop timestamps outside the window
    if len(self._timestamps) < self.max_calls:
        return 0.0                            # room now
    return self.window_seconds - (now - self._timestamps[0])

def record(self, now):
    self._timestamps.append(now)

Why a sliding window

A fixed bucket allows bursts at boundaries; a sliding window smooths traffic to a true rate, which is what avoids tripping BC's throttling.

class BCMinIntervalLimiter · class BCRateLimitGroup

BCMinIntervalLimiter enforces a floor of min_interval_seconds between consecutive requests. BCRateLimitGroup combines the tiers: try_acquire() takes a slot only if every tier is clear and otherwise returns the longest wait; acquire(max_wait=…) sleeps between attempts, holding nothing, and gives up with the projected wait once it would exceed max_wait.

bc_rate_limiter = BCRateLimitGroup(
    BCMinIntervalLimiter(min_interval_seconds),   # ≥ 4s between visits
    BCRateLimiter(short_max, 60),                 # burst cap
    BCRateLimiter(hourly_max, 3600),              # hourly ceiling
    batch_limiters=(
        BCRateLimiter(hourly_max * 0.7, 3600),    # batch share: 350 of 500
    ),
)
Invariant

The check and the record in try_acquire() contain no await, so on the event loop they are atomic and need no lock — and so nothing ever sleeps while holding one. The group is still acquired before the scrape slot (see _run_scrape): a caller waiting for the hourly cap must never hold the slot the rest of the service is waiting on.

Circuit breaker

After BATCH_PAUSE_AFTER_BLOCKED consecutive blocked results, every active job is paused with a reason and one Telegram alert is sent. The worker then probes a single item at growing intervals (30 s doubling to 15 min); a blocked probe costs the item no attempt. A successful probe — or any live /address success since the pause — resumes the jobs. Per-address not_found/blocked alerts are suppressed for batch items so an import cannot flood Telegram.

Invariant

Batch never makes the service faster or ruder towards BC than a client loop: it waits instead of shedding, keeps the 4 s spacing, and is capped at 70% of the hourly budget.

Batch app/services/scrape_gate.py

The single scrape slot that replaced Semaphore(1). Still single-flight; the only change is who goes next.

A live request registers demand as soon as it starts waiting — including while it waits for a rate-limit token. A batch caller takes neither the slot nor a token while any live demand exists. Batch app/services/webhook.py

Tells the caller a job finished, with an HMAC-signed POST of {job_id, state, total, progress} — no property data. Built from the standard library plus the existing httpx.

Signs the raw body as X-BC-Signature: sha256=<hmac> and retries non-2xx replies three times with backoff. Delivery reuses the Telegram module's background-task holder, so it is never garbage-collected mid-flight and is flushed on shutdown.

SSRF guards

https only; host must be on BATCH_CALLBACK_ALLOWED_HOSTS; no credentials in the URL; redirects never followed; 5 s timeout; hosts resolving to private, loopback or link-local addresses are refused. With no allowlist or no secret, webhooks are off and a submit asking for one gets 400.

Batch app/routes/batch.py · app/db/batch.py

The HTTP surface and the persistence behind it.

Data app/db/connection.py

Owns the SQLite connections (one per thread) and the schema DDL, so the runtime and the setup script can never drift. The schema is CREATE TABLE IF NOT EXISTS throughout and is re-applied on connect.

SCHEMA · init_db(path) · db_path()

Defines four tables — assessment_cache (successes), failed_lookups (failures + negative cache), and batch_jobs / batch_items (batch work) — and applies them idempotently, in WAL mode. setup_db.py reuses this exact DDL.

Why the schema lives here

Because the runtime and the migration script apply the same string, a database created before failed_lookups existed gains the table simply by connecting. There is no separate migration to forget.

get_connection() — one connection per thread, WAL mode

Returns this thread's long-lived connection (created lazily under a lock), tuned for a mixed read/write workload. DB calls run in asyncio.to_thread workers, so each worker thread keeps its own.

conn = sqlite3.connect(path, check_same_thread=False, timeout=15.0)
conn.execute("PRAGMA journal_mode=WAL")      # a write never blocks a read
conn.execute("PRAGMA synchronous=NORMAL")
conn.execute("PRAGMA busy_timeout=15000")

Why one connection per thread + WAL

The old code opened and closed a connection on every cache read/write; long-lived connections remove that churn. They must not be shared between threads, though: two threads querying one connection at once can interleave, and one receives the other's row. That surfaced as an IndexError in cache_get once batch submit and the batch worker read concurrently. Per-thread connections are the standard answer; WAL gives concurrent readers and busy_timeout serializes writers. reset_for_tests() closes them all so a test can point at a throwaway DB.

The fix — a contributing factor

The server previously ran SCRAPE_CACHE_TTL_SECONDS=3600, so every cached address was re-scraped hourly even though BC data changes about once a year. That multiplied traffic and the odds of being throttled. The default is now 0 — never expire.

def _next_retry_at(attempts):
    minutes = min(15 * 2**(attempts-1), 24*60)   # 15m, 30m, 60m … capped at 24h

Why backoff

A transiently blocked or slow site should be retried gently, not hammered. Exponential backoff spaces retries out; the 24-hour cap keeps a permanently-broken address from drifting to never.

Observability app/services/telegram_notify.py

The Telegram transport: fire-and-forget delivery that can never raise into, or block, a lookup.

send_telegram_message_background(text) — strong task refs

Schedules the async send without awaiting it, and keeps a strong reference to the task until it finishes.

task = loop.create_task(send_telegram_message(text))
_background_tasks.add(task)                       # asyncio holds only a WEAK ref —
task.add_done_callback(_background_tasks.discard) # without this the alert can be GC'd mid-flight

The subtle bug this avoids

asyncio keeps only a weak reference to a running task, so a bare create_task can be garbage-collected before it sends and the alert is silently lost. Holding a strong reference until the done-callback fires is the documented fix.

_enabled() · send_telegram_message() · flush_pending()

_enabled gates everything on a token and at least one chat id being configured, so a stock deployment stays silent rather than erroring. send_telegram_message posts to each chat and swallows per-recipient failures. flush_pending waits briefly for in-flight sends on shutdown.

def _enabled():
    return bool(settings.telegram_bot_token and settings.get_telegram_chat_ids())
Invariant

Alerting is best-effort and isolated: no Telegram failure — bad token, network blip, no event loop — is ever allowed to surface as a lookup error. Monitoring must not become a source of outages.
